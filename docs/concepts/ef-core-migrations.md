# EF Core and schema migrations

> Field Guide: §9.9 Schema Migrations, §9.5–9.8 Keys, Constraints and Defaults, §9.14 ORM ("while monitoring generated queries"), §22.21 Database Migration Pipeline · Introduced in: M2
> Code: [`Data/FluxDbContext.cs`](../../src/Flux.Gateway/Data/FluxDbContext.cs), [`Data/Migrations/`](../../src/Flux.Gateway/Data/Migrations/), [`Data/DatabaseStartup.cs`](../../src/Flux.Gateway/Data/DatabaseStartup.cs), [`Data/DesignTimeDbContextFactory.cs`](../../src/Flux.Gateway/Data/DesignTimeDbContextFactory.cs)

## Problem
The schema has to exist, identically, on a laptop, in CI's throwaway containers and on Megatron, and it has to *change* over time without anyone running SQL by hand. "Which `ALTER TABLE`s has this database had?" must have a definite answer.

## Context
Every service with a relational database has this problem. Tools: EF Core migrations (.NET), Flyway/Liquibase (JVM), Alembic (Python), Rails migrations. They all share one idea: **numbered change scripts plus a history table in the database**.

## Solution
```
C# model (FluxDbContext) ──dotnet ef migrations add──▶ 20261015…_InitialSchema.cs   (committed)
                                                       FluxDbContextModelSnapshot.cs (the model "as of now")
database: __EFMigrationsHistory ──"which have I run?"──▶ MigrateAsync() runs only the missing ones, in order
```
- `migrations add` **diffs** the current model against the snapshot and writes the difference as code. You review it like any other code.
- `MigrateAsync()` reads `__EFMigrationsHistory`, applies the missing migrations, each in a transaction, and records them.
- Seed data that must exist **everywhere** (the plans and their limits) lives in the model (`HasData`), so it ships *inside* the migration. Demo merchants don't: they're dev-only and come from `DevSeed`, outside the migration.

### Read the SQL, always (§9.14)
`dotnet ef migrations script` shows the exact SQL. Doing that in M2 caught a real bug before it was ever committed:

```sql
-- what EF generated by default:
CONSTRAINT fk_merchants_plans_plan_id FOREIGN KEY (plan_id) REFERENCES plans (id) ON DELETE CASCADE
```
`CASCADE` on a required foreign key is EF's default. Here it means **deleting the `free` plan would silently delete every free merchant**, and through `api_keys` → `merchants`, their keys too. The spec's SQL has plain `references` (no cascade), so every FK is now `.OnDelete(DeleteBehavior.Restrict)`: deleting a plan that's in use fails loudly instead.

### Who runs migrations, and when
| Where | How | Why |
|-------|-----|-----|
| Laptop / Compose | `Database:MigrateOnStartup=true` (Development config) | Zero ceremony: `docker compose up` gives you a working schema |
| Integration tests | `PostgresFixture` migrates once per test run | Dozens of gateway hosts migrating the same database in parallel would only test the migration lock |
| Megatron (M7) | A **separate Job** (an EF *migration bundle*) before the rollout | 3 replicas migrating on startup would race, and the request-serving process would need DDL rights (§22.21, spec §17) |

## Alternatives
| Option | Trade-off |
|--------|-----------|
| Hand-written SQL files + a runner (DbUp, Flyway) | You see exactly what runs, and the SQL can do anything. You also write every diff yourself. A great fit if you prefer SQL-first. |
| `EnsureCreated()` | Creates the schema once, but can never *evolve* it. Only for throwaway prototypes. |
| Dapper, no ORM | Explicit SQL on every query. ADR-0001 chose EF Core for migrations and bundles; the hot path barely touches the database anyway. |

## Trade-offs
- **Generated code is still your code.** The `CASCADE` story is the reason to read every migration.
- **Snake case** (`EFCore.NamingConventions`) keeps the database idiomatic for anyone using `psql` (`plan_id`, not `"PlanId"`), at the cost of one more package.
- **Enums as lowercase text** (`'active'`) with a `CHECK` constraint: readable and self-documenting in SQL. The cost is a value converter, which is why `Enum.TryParse` is avoided at the API edge: it would also accept `"1"`.

## Implementation
- **`IDesignTimeDbContextFactory`**: without it, `dotnet ef` would *boot the gateway* to find the model, which needs config and a reachable database. The factory builds the context directly. Creating a migration never connects, so its connection string is a placeholder.
- **`AddPooledDbContextFactory`**: the auth middleware is a singleton. It borrows a context from a pool for a single cache-miss query and returns it. A scoped `DbContext` would need a scope per request even when the cache answers.
- **Central transitive pinning**: Npgsql's provider asks for EF Core ≥ 10.0.4 while the design package brings 10.0.13. Two versions of the same assembly broke the build (`MSB3277`, and warnings are errors). `CentralPackageTransitivePinningEnabled` plus one `PackageVersion` pins EF Core everywhere.

## Testing
- Every integration test runs against the **migrated** schema in a real PostgreSQL 17 container (Testcontainers), so a broken migration fails CI.
- `The_migration_seeds_the_plans_from_the_spec` checks the seeded limits against spec §6.
- `The_database_itself_rejects_an_invalid_merchant_status` checks the `CHECK` constraint survived the trip from C# to SQL.

## Commands
```bash
dotnet tool restore                                   # installs dotnet-ef from dotnet-tools.json
dotnet ef migrations add <Name> --project src/Flux.Gateway --output-dir Data/Migrations
dotnet ef migrations script --project src/Flux.Gateway   # the SQL that would run
```

## Observability
The gateway logs the migrations it applies at startup (Development). In M7 the migration Job's logs and exit code are the record.
